Let AI Write the Code. Keep the Engineering.

AI has changed software development.

That part is no longer controversial.

We can ask an AI coding assistant to explore a codebase, write a feature, generate tests, fix failures, refactor code, and even review its own work. Tasks that used to take hours can sometimes be completed in minutes.

But something interesting is happening.

For many developers, AI is not making development faster. It is making it slower.

A colleague recently told me that tasks that used to take him 6–8 hours can now take 8–12 hours when he uses AI. The tool that was supposed to save time became another source of work.

And I don't think the problem is that AI is bad. I don't think the problem is that the developer is bad either.

I think we are learning a new engineering discipline.

The problem is not the code

A common AI-assisted workflow looks something like this:

Take a Jira ticket.
Give it to an agent.
Let the agent ask questions.
Let it build a prompt.
Let it create a plan.
Let it implement the plan.
Run the tests.
If something fails, retry.
Repeat until everything passes.

It sounds great. And sometimes it is great.

For a small, isolated task, there is nothing wrong with letting an agent do most of the work.

The problem starts when this workflow becomes the default way of developing software.

At some point, the engineer stops making decisions and starts watching the system make decisions for them.

The code may work. The tests may pass. The pull request may even look perfectly reasonable.

But can the engineer explain why the solution looks the way it does?

Do they know whether the same problem was already solved somewhere else? Do they know what assumptions the AI made? Do they know what trade-offs were introduced? Do they know whether the solution fits the architecture?

And perhaps most importantly: do they know what the machine actually did?

Passing tests is not the same thing as having a good solution.

The real problem: we are bad at delegation

I initially thought this was mainly a problem of "AI control."

I now think that is too narrow. The deeper problem is delegation.

Software engineers have always delegated work. We delegate to junior developers, senior developers, specialists, external services, build systems, compilers, static analyzers, and automated test suites.

AI is simply the most capable executor we have ever had.

And that creates a new problem.

When you delegate work to another engineer, you normally spend some time explaining the problem before saying:

"Go build it."

You discuss the context. You discuss constraints. You ask whether something similar already exists. You make sure the person understands the goal.

You don't usually hand someone a Jira ticket and disappear until they come back with a green test suite.

Yet this is exactly what we often do with AI. We ask it to build first.

Don't start with "build this"

One of the biggest changes in my own workflow has been very simple:

I try not to start with implementation.

Instead of:

"Implement this feature."

I start with:

"Let's understand this problem first."

What are we missing? Do we have enough information? Is there already a similar implementation? Could the problem already be solved somewhere in the system?

What parts of the existing architecture are relevant? Are there constraints we haven't considered? Could this solution conflict with something that already exists?

What are the possible approaches? What are the risks?

Only after these questions have been discussed do I want a plan. And only after the plan makes sense do I want implementation.

The workflow becomes:

Research → Discussion → Plan → Implementation → Verification

rather than:

Task → Generate → Fix → Retry → Done

That small change has a surprisingly large effect.

The AI is still doing most of the typing. But the engineer is doing the engineering.

You don't need to read every line

There is an important distinction here.

Keeping control does not mean manually reviewing every line of AI-generated code. That would completely miss the point of using AI.

A machine can read and generate code much faster than I can. The valuable human activity is higher-level.

I want to understand:

  • what the solution is doing;
  • why it was chosen;
  • what changed in the system;
  • what assumptions it relies on;
  • what risks it introduces;
  • what happens in unusual cases;
  • whether the result actually solves the original problem.

The question is not:

"Did I read every line?"

The question is:

"Do I understand the engineering decision the machine just made?"

That is the kind of control I want to keep.

AI should be an executor, not the owner of the process

This changes the role of the engineer.

When AI writes most of the code, the engineer's job moves up a level.

Less typing. More thinking. Less implementation. More direction. Less manual execution. More delegation and verification.

In my current workflow, I would roughly describe it as 80% discussion and reasoning and 20% supervising implementation.

The numbers aren't important. The shift is.

The engineer doesn't disappear from the process because AI can write code. The engineer becomes responsible for deciding what should be written in the first place.

From individual habits to team protocols

This is where I think the next step is.

It is not enough for one developer to develop good AI habits. Teams need shared ways of working.

Instead of telling developers:

"Use AI responsibly."

we should define actual protocols for AI-assisted development.

A protocol should answer questions such as:

  • What must happen before implementation starts?
  • What information should the AI have?
  • Which decisions require human approval?
  • Which tasks can be fully automated?
  • What must be verified before a task is considered complete?
  • What happens when the implementation fails?
  • When should the system stop and ask a human?

The important part is that these should not be just suggestions inside a prompt.

Where possible, the process should enforce them.

What an AI development protocol can look like

Imagine a team establishes a simple workflow.

1. Research comes first

An agent receives a task but cannot immediately start writing code.

It first has to inspect the relevant parts of the codebase, understand existing patterns, and identify dependencies.

Only then can it propose a solution.

2. The plan is a checkpoint

The agent produces a plan based on its research.

The plan is not automatically accepted.

Someone — ideally the engineer responsible for the task — decides whether the plan makes sense.

3. Work happens in small steps

The plan is split into independent tasks. Each task follows the same basic lifecycle:

Implement → Test → Review → Complete

This prevents one enormous autonomous operation from running through an entire feature without meaningful checkpoints.

4. Verification is independent

The same agent that writes the code should not be the only source of truth about whether the code is good.

Testing and review can be separate steps, potentially performed by separate agents.

The goal isn't to create an army of agents for the sake of it. The goal is to introduce independent checks into the process.

5. Failure requires a decision

When something fails, the system should not blindly retry forever. It should determine what happened.

Maybe the implementation is wrong. Maybe the original plan was wrong. Maybe the requirements are incomplete. Maybe the task itself needs clarification.

The possible outcomes should therefore include:

retry → re-plan → ask the human → stop

A failure becomes a decision point rather than another automatic loop.

Make the rules harder to break

There is another important lesson here.

If a rule is important, don't rely entirely on the AI remembering it.

For example, if only a particular stage of the workflow should be allowed to run tests, enforce that through permissions.

If an agent should not modify certain project state, don't just tell it not to.

If only a designated coordinator should communicate decisions back to the engineer, make that part of the architecture.

In other words:

Don't just prompt the process. Design the process.

A good protocol should survive an imperfect model.

The AI can misunderstand an instruction. It can forget context. It can make a wrong assumption.

The guardrails should still hold.

The goal isn't less automation

None of this is an argument against autonomous AI. Quite the opposite.

I want AI to do as much work as possible.

I want it to research. I want it to write code. I want it to run tests. I want it to find bugs. I want it to review implementations. I want it to do the boring work that humans are bad at.

But I don't want to delegate the decisions that define the engineering outcome simply because the machine is capable of executing them.

There is a difference between delegating execution and delegating responsibility.

We should automate the first as aggressively as possible. We should be much more careful with the second.

The engineer is not becoming less important

AI has changed software development, and I don't think there is any going back.

The amount of code written manually will probably continue to decrease. The amount of autonomous work will probably continue to increase. And AI agents will become dramatically better.

But that doesn't make engineering less important. It makes engineering judgment more important.

The strongest engineers of the AI era may not be the ones who can write the most code. They may be the ones who can:

understand the problem, ask the right questions, delegate effectively, recognize a good solution, reject a bad one, and design a process that keeps humans responsible for the outcome.

Let AI write the code.

Keep the engineering.
